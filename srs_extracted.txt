Executive summary
The Standard Video Player is an Android-first, cross-platform media application designed around a 
responsive, immersive video player, a dedicated audio experience, a searchable local library, Google Drive 
media access, utility tools, an encrypted Secret Vault and a layered administration/security environment. The 
application is intended to provide a strong everyday playback experience without exposing advanced controls 
to users who do not need them.
The product will use Flutter and Dart for the application and user interface, with native Kotlin/Android 
integration and C/C++ components for performance-sensitive playback, codec, rendering and media-
processing work. The implementation should build on proven media engines and codec libraries rather than 
attempting to create an entire decoding stack from scratch. Exact engine/library selections remain subject to 
compatibility, licensing, maintenance and device-benchmark evaluation.
The primary navigation contains Video, Audio, Tools and Settings. The default landing page is the Video 
Library. The app supports local device media and Google Drive as media sources. Broader cloud-provider 
support is intended for encrypted backup storage, not as a general replacement for the explicitly limited 
media-source model. YouTube, YouTube Music, SMB/NAS, DLNA and arbitrary network shares are outside 
scope.
Standard mode presents essential playback and library functions. Pro Mode is freely available and exposes 
advanced user-facing controls such as expanded equalizer and color controls, audio/video profiles and 
advanced enhancement settings. Development Mode is separately gated, time-limited and device-bound; it 
provides experimental processing and hardware override tools and is activated online through a server-
authoritative approval process.
The security model includes a transactional encrypted Secret Vault; encrypted local and cloud backups; 
device-bound administrator sessions; multi-factor administrator login; tamper-evident audit logs; role-based 
access; controlled recovery; and emergency lockdown. Backup data is compressed before encryption, each 
backup receives an independent encryption key, and cloud replicas are verified before the primary copy is 
removed.
Important engineering boundary
The requirements specify intended behavior, not impossible guarantees. Android cannot guarantee a permanent 
hardware identity, force a disconnected device to receive a remote command, physically erase every flash-storage 
remnant, or guarantee that an unsupported cloud provider exposes all required APIs. The implementation must use 
cryptographic device binding, signed metadata, local expiry enforcement, secure key management and provider 
capability checks, while clearly reporting residual limitations.
1. Purpose, scope and product vision
1.1 Purpose
This SRS establishes a shared implementation baseline for the Standard Video Player. It defines what the 
product must do, how its major subsystems interact, which security and operational controls are required, 
and how completion can be verified. It is intended to reduce ambiguity between product, design, engineering 
and QA.

1.2 Product vision
Deliver a polished, responsive and immersive media player that handles local and Google Drive media, 
supports advanced playback and enhancement on capable devices, includes a first-class audio experience, 
and provides dependable privacy, backup and recovery features. Everyday playback should remain 
straightforward; advanced and experimental capability should be isolated behind Pro and Development Mode 
surfaces.
1.3 In-scope capabilities
 Video playback with HW, HW+, SW and hybrid decoder strategies; responsive immersive controls; 
gestures; resume; bookmarks; playback profiles; HDR handling; frame stepping; A-B repeat; PiP and 
floating playback.
 Dedicated audio library and player with background playback, queues, playlist import/export, output 
profiles, equalizer, lyrics, sleep timer and video-as-audio operation.
 Local library scanning and indexing with folder exclusions, hidden-file preference, duplicate detection, 
search, filters, sorting and user-customizable layouts.
 Google Drive browsing and streaming, optional original-quality offline download, upload/save-back, 
network controls and time-limited offline-copy governance.
 Utility tools for conversion, audio extraction, frame extraction, subtitle processing, media inspection and 
batch jobs.
 Pro Mode, Development Mode, graphics capability detection, multi-stage upscaling, deblur, denoise and 
experimental processing.
 Encrypted Secret Vault with transactional file movement, auto-lock, privacy protections and account-
based recovery.
 Local and cloud app backups, restore points, storage offloading, provider integration, administrative 
exports and recovery.
 Role-based administrator console, protected ownership, 2FA, device management, session controls, audit 
trails, security monitoring and global lockdown.
1.4 Explicitly out of scope
 YouTube or YouTube Music streaming, downloading, extraction, background playback or account 
integration.
 SMB, NAS, DLNA or arbitrary network-share playback as media sources.
 Building a complete proprietary codec/decoder engine from first principles.
 Guaranteed recovery of data after loss of all device keys and all valid backups.
 Guaranteed physical secure erase of flash storage or guaranteed remote enforcement while a device 
remains disconnected.
 Automatic silent installation of APK updates; users must approve and install updates manually.

3.2 Role model
ROLE-01  [Must] The administrator system shall implement Super Admin, Admin and Support Admin roles with 
distinct permission sets.
ROLE-02  [Must] There shall be no public administrator registration. Admin identities must be pre-approved 
Google accounts with mandatory 2FA.
ROLE-03  [Must] The system shall support a maximum of three Super Admin accounts. The protected owner/Main 
Admin is one of these accounts.
ROLE-04  [Must] The protected-owner designation may transfer to either authorized Super Admin only after 
mutual approval by the relevant existing Super Admins. The previous protected owner remains a Super Admin 
unless separately and explicitly changed.
ROLE-05  [Must] The Main Admin alone may connect additional backup-storage providers/accounts and change 
the recovery code. Either Super Admin may independently trigger or deactivate global lockdown under the 
required reauthentication controls.
ROLE-06  [Must] Either Super Admin may grant delegated backup-restoration permission. Backup export and 
backup restoration shall remain separate permission capabilities.
ROLE-07  [Must] Support personnel shall not receive secrets, recovery codes, raw biometrics, private keys or 
unrestricted access to private media.
ROLE-08  [Must] The protected owner shall not be removed or disabled by another Super Admin while protected. 
Any transfer of the protected-owner designation shall follow the mutual-approval workflow; the former owner 
remains a Super Admin unless separately changed.
4. Product scope, assumptions and constraints
4.1 Platform strategy
 Android is the first implementation target. The product architecture should remain cross-platform where 
the selected media, storage and security abstractions permit.

 Flutter/Dart provides the primary UI and application state management. Kotlin provides Android lifecycle, 
permissions, storage access, notifications, media session, foreground service and platform API integration.
 C/C++ is used for media engine integration, decoder/rendering paths and performance-sensitive 
processing. A narrow FFI/NDK boundary should keep UI code independent of native implementation 
details.
 The initial distribution model is direct APK delivery. The app should check for updates and notify the user, 
but the user manually downloads and approves installation.
4.2 Device and OS constraints
 Android scoped storage and runtime permissions constrain which files can be indexed. The application 
must request only permissions justified by a feature and use the system file/folder picker where practical.
 Hardware decoder, Vulkan, NPU, HDR output, audio passthrough, external displays and refresh-rate 
matching are device- and OS-dependent. Capability detection must precede feature exposure.
 Android Keystore may provide hardware-backed key protection on supported devices; the app must 
detect and report the actual security level rather than assuming hardware backing.
 An Android device identifier is not a universal permanent hardware identity. Device binding must use 
registered cryptographic keys and risk signals in addition to platform identifiers.
4.3 Network and integration constraints
 Local playback must function offline. Development Mode activation, Google Drive browsing, online 
subtitle services, updates, cloud backups and cross-device sync require network connectivity.
 Google Sign-In identity, Google Drive media access and backup cloud-provider connections are separate 
authorization contexts. A Google account login does not automatically authorize Drive file access.
 Cloud backup providers must be integrated using supported official APIs or a vetted connector. Where an 
API cannot support required upload, download, listing, deletion or verification operations, that provider 
must be marked unsupported or partially supported rather than accessed through brittle scraping.
 Proton Drive multi-account support is a desired provider capability and must be validated against 
available official integration options before implementation commitments are made.
4.4 Licensing and distribution constraints
Before selecting mpv, FFmpeg, Media3/ExoPlayer, codec packs, AI models or graphics libraries, engineering 
must complete license, attribution, redistribution and patent-risk reviews appropriate to the intended 
distribution model. GPL/LGPL obligations, codec patents and third-party model terms must be assessed by 
qualified reviewers. This SRS does not grant any third-party license.

5.2 Native boundary and engine strategy
ARCH-01  [Must] The UI layer shall communicate with the native media core through a versioned, typed interface 
(FFI/platform channel/native plugin) rather than direct scattered native calls.
ARCH-02  [Must] The media core shall expose a stable abstraction for source, decoder, renderer, audio output, 
tracks, seek, playback state and error events.
ARCH-03  [Must] The implementation shall evaluate established media engines and codec libraries. It shall not 
reimplement all codec decoding functionality from scratch.
ARCH-04  [Must] Decoder selection shall support HW, HW+, SW and hybrid strategies where supported by the 
chosen engine/device. The selection policy shall be observable in diagnostics.
ARCH-05  [Must] Native processing modules shall be isolated so that deblur, denoise, scaling, sharpening and color 
processing can be enabled, disabled, benchmarked and replaced independently.
ARCH-06  [Must] GPU/NPU/CPU paths shall be capability-probed and validated. Unsupported paths must fall back 
safely without blocking ordinary playback.
5.3 Backend authority
The backend is authoritative for administrator roles, Dev Mode activation/expiry/revocation, protected-owner 
state, offline-download extension approvals, admin recovery records, audit events and cloud backup 
metadata. A mobile client must not be able to grant itself Dev Mode, extend an expiry, alter administrator 
roles or erase audit history by editing local data.

7. Functional requirements
7.1 Startup, permissions and settings
APP-01  [Must] On first launch, onboarding shall explain the permissions needed for the initial library/player 
experience and request those necessary permissions. Feature-specific permissions that cannot or should not be 
requested at startup shall be requested when the related feature is first used, following Android policy.
APP-02  [Must] The app shall provide a settings switch for background audio playback.
APP-03  [Must] The app shall provide individual notification preferences and a master notification switch.
APP-04  [Must] The app shall ask for consent during first installation/onboarding before collecting analytics or 
usage data. If consent is denied, collection must remain disabled. Consent must be changeable later in Settings.
APP-05  [Must] Crash reports and diagnostic reports shall require explicit per-report consent unless the user 
separately enables a future-consent preference. A crash dialog shall clearly state that the app crashed and offer an 
optional report submission.
APP-06  [Must] App data clearing shall offer a backup opportunity and then allow the user to proceed only after 
explicit confirmation.
APP-07  [Must] App launch lock shall be optional and support PIN and device biometric authentication.
APP-08  [Must] The app shall ask for explicit confirmation before deleting any media file. Duplicate cleanup and 
repair utilities shall not delete original files without confirmation.
7.2 Local media sources and scanning
LIB-01  [Must] The app shall scan all accessible media locations by default, subject to Android permission and 
scoped-storage rules.
LIB-02  [Must] Users shall be able to filter included folders and exclude folders and file types.
LIB-03  [Must] Hidden files and folders shall be excluded by default, with an opt-in setting to include them.
LIB-04  [Must] The scanner shall detect newly added media automatically where OS facilities permit and shall also 
run scheduled full rescans.
LIB-05  [Must] The scanner shall identify likely duplicate files and offer to hide duplicate library entries or remove 
an entry. It shall not silently delete the underlying media file.
LIB-06  [Must] The library shall store media references and technical metadata in a local database; it shall not 
unnecessarily copy source media into the app data directory.
LIB-07  [Must] The scanner shall tolerate inaccessible, transient, unsupported or corrupted files and continue 
scanning other items.

7.3 Video playback
VID-01  [Must] The player shall provide an immersive full-screen mode that uses the available display area and 
adapts responsively to device dimensions.
VID-02  [Must] The video title shall remain hidden during immersive playback unless the user explicitly opens 
information or playback controls.
VID-03  [Must] A single tap shall reveal standard controls; controls shall auto-hide after a configurable short delay.
VID-04  [Must] Standard controls shall include Play/Pause, Previous Video and Next Video. Previous/Next shall 
switch media items and shall not act as 10-second seek controls.
VID-05  [Must] Double-tap on the left or right playback area shall seek backward or forward by 10 seconds 
respectively.
VID-06  [Must] The player shall support HW, HW+, SW and hybrid decoder modes where supported, with 
automatic selection and fallback after a decoder failure.
VID-07  [Must] On a hardware-decoder failure, the player shall automatically attempt a compatible alternative 
decoder path, including software or hybrid mode where appropriate.
VID-08  [Must] For damaged frames, the player shall attempt recovery; if recovery fails, it shall skip the damaged 
frame and continue where safe.
VID-09  [Must] On a playback failure, the player shall retry through another compatible playback method before 
surfacing an unrecoverable error.
VID-10  [Must] On unexpected crash, the app shall clearly disclose the crash and offer optional report submission. 
The report must not be sent without consent.
VID-11  [Must] The player shall support the widest stable playback-speed range exposed by the engine and device. 
The UI shall validate the actual supported range rather than promising a fixed maximum.
VID-12  [Must] The player shall support dedicated previous-frame and next-frame controls where frame stepping 
is supported by the active engine.
VID-13  [Must] The player shall support A-B loop markers and repeat playback between the selected timestamps.
VID-14  [Must] The user shall be able to choose resume behavior in Settings. The app shall not repeatedly ask on 
every playback start.
VID-15  [Must] Playback history shall be retained indefinitely until the user clears it. Resume positions shall be 
saved with sufficient precision for practical restoration.
VID-16  [Must] The player shall support global or per-video brightness and volume preferences, configured in 
Settings rather than prompted every time.
VID-17  [Must] The player shall follow device orientation by default and provide a temporary rotation control.
VID-18  [Must] The player shall support Android Picture-in-Picture and a separate floating player window where 
permitted by OS/device policy.
VID-19  [Must] The player shall match display refresh rate to video frame rate where supported, with safe fallback 
if the OS denies or does not support the request.
VID-20  [Must] The player shall use best supported HDR output when the display path supports HDR; otherwise it 
shall tone-map HDR content to SDR.
VID-21  [Must] The player shall expose expandable panels for subtitles, audio tracks, speed, aspect ratio, rendering 
and enhancement options. Advanced controls shall not overwhelm the default screen.
VID-22  [Must] The player shall support Eco, Balanced and Performance playback modes. Automatic 
thermal/battery adaptation shall be available with a manual override option.

AUD-02  [Must] Audio playback shall support background playback and screen-off playback. Users shall control

AUD-03  [Must] The audio player shall expose configurable headset/Bluetooth media controls, including

AUD-04  [Must] The audio player shall support automatic folder progression and a user-managed playback queue.

10.2 Transactional move into Vault
1.  Obtain the relevant file/folder access authorization and verify the source can be read.
2.  Create a unique staging record and encrypt into private app storage. Do not delete or overwrite the source 
at this stage.
3.  Calculate and verify integrity/authentication metadata for the encrypted result; confirm all expected bytes 
and metadata are present.
4.  Commit the encrypted vault object and metadata atomically, or mark the transaction incomplete if the 
commit fails.
5.  Only after a successful commit and user-authorized move operation may the app delete the original file. If 
any step fails, roll back staging and preserve the original.
6.  On crash recovery, detect incomplete transactions and either complete verification or restore a safe pre-
commit state. Do not create duplicate canonical vault entries.
Flash-storage limitation
Application-level deletion can remove directory references and overwrite accessible temporary data, but flash 
translation layers, snapshots and wear-leveling may retain physical remnants. The app must never promise forensic-
grade physical secure erase.

16. Key workflows and state transitions
16.1 Playback and decoder fallback
1.  User selects a local or Google Drive media item.
2.  The source adapter validates access and retrieves metadata/stream information.
3.  The capability manager probes available decoders, rendering paths, HDR support and output route.
4.  The policy selects HW, HW+, SW or hybrid path based on compatibility and prior failure signals.
5.  Playback starts and emits status/diagnostic events.
6.  If decoding or rendering fails, the recovery controller retries an alternative compatible path.
7.  If damage remains, attempt frame recovery and skip irrecoverable frames where safe.
8.  If all paths fail, show a clear error with optional consent-based report submission.
16.2 Vault move transaction
1.  Authorize source read/write access.
2.  Create transaction ID and encrypted staging output.
3.  Stream encryption and calculate authenticated integrity state.
4.  Verify staged ciphertext and metadata.
5.  Atomically commit canonical Vault object.
6.  Only then delete original when the user explicitly selected move.
7.  On error/crash, preserve source and safely clean or resume staging.
16.3 Offline Drive expiry
1.  User downloads the original-quality file and selects destination.
2.  Backend records stable Drive ID, owner, metadata, original timestamp and initial 30-day expiry.
3.  Client stores signed expiry metadata and schedules daily in-app and OS notices.
4.  Within the five-day grace period, the user may request an extension by designated email.
5.  Admin approves one extension of 1-30 days for all offline downloads of that user, or rejects the request.
6.  If rejected, the user is notified immediately and may submit a new request while grace remains.

7.  If no approval is valid at deadline, local offline copy is deleted at the next enforceable opportunity; original 
Drive file is untouched.
8.  Next monthly approval cycle is scheduled from the resulting policy timestamp.
16.4 Backup offload
1.  Primary backup storage usage is monitored.
2.  At 70% usage, select oldest eligible backups and calculate the minimum amount to offload.
3.  Choose the currently designated secondary account and test its health/capabilities.
4.  Compress if not already compressed, encrypt locally, upload and verify integrity/retrieval.
5.  Only after successful verification, remove primary archive while retaining manifest and restore-point 
reference.
6.  If the account is disconnected/full/unavailable, pause and ask the Main Admin whether to use another 
account or stop.
7.  If primary storage reaches the 5 GB cap without safe offload capacity, request Main Admin decision to 
replace eligible older backups or add storage.
16.5 Administrator recovery
1.  Super Admin begins recovery from an available device or recovery interface.
2.  The service challenges the registered device key and verifies cryptographic device ownership and 
historical registration.
3.  If device proof succeeds, restore the authorized account access path after risk checks.
4.  If device verification is unavailable or fails, request the recovery/reset code.
5.  A valid recovery code permits controlled access reset, email replacement/addition and encrypted 
administrator-backup import.
6.  Record all attempts, verification results and resulting changes in immutable audit history.
7.  Notify the appropriate administrators according to the recovery-notification policy.
16.6 Global lockdown
1.  Either Super Admin initiates lockdown and reauthenticates as required.
2.  Backend marks protected operations and configured access paths as locked down.
3.  Sessions/tokens may be restricted or revoked according to incident policy.
4.  Both Super Admins receive email, dashboard and push alerts.
5.  Every three hours, both receive a current security report while lockdown remains active.
6.  Either Super Admin may deactivate after fresh auth, 2FA, master code and a recorded reason.

18.2 Mandatory failure-injection scenarios
 Kill the process during Vault staging, commit and original deletion phases.
 Interrupt a cloud upload at several offsets and verify that incomplete objects are not considered valid 
replicas.
 Corrupt a backup manifest, ciphertext block or authentication tag and verify rejection plus previous-valid-
backup fallback.
 Expire a Drive offline copy while the device is offline, then reconnect and verify signed expiry 
enforcement and original-file preservation.
 Attempt a third administrator device session and verify explicit choice of session to terminate.
 Revoke an administrator device and verify immediate session/token invalidation.
 Attempt admin audit modification/deletion through UI and API; verify denial and audit of the attempt.
 Force a decoder failure and verify alternate decoder path without losing playback position unnecessarily.
 Run processing under low battery/high thermal state and verify adaptive reduction/override behavior.
